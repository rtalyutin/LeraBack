# LeraBack — общая база салонов

Один backend и одна PostgreSQL обслуживают несколько салонов. В Timeweb создаются два приложения: LeraBack и LeraFront; они используют уже существующую базу tg-mcp, отдельную SQL-схему `lera`. Все салоны Lera остаются в общих таблицах внутри этой схемы.

## Отдельная SQL-схема

Dockerfile уже задаёт `DATABASE_SCHEMA=lera`: в Timeweb эту переменную вводить не нужно. Выбирается заранее созданная схема, принадлежащая пользователю Lera. Все подключения, миграции, временные представления и функции используют эту область; чужие таблицы `public` не являются схемой приложения. Для существующей установки в `public` явно переопределить `DATABASE_SCHEMA=public`. Локальные команды вне Docker без переменной сохраняют legacy-значение `public`. Новое имя схемы не переносит существующие данные автоматически. Системные схемы и некорректные идентификаторы отклоняются. Для Lera не нужны PostgreSQL-расширения; существующие расширения других приложений не меняются. Подготовка роли/схемы и параметры двух приложений описаны в `TIMEWEB.md`.

## Что хранится вместе

`accounts` — общие аккаунты, `salons` — реестр салонов, `salon_memberships` — доступ аккаунта к одному или нескольким салонам. Аккаунты создаёт разработчик; вошедший администратор сам создаёт салон и получает членство в нём. Существующий `admin_users` остаётся совместимым представлением аккаунтов; действующие сессии сохраняются.

Услуги, профили мастеров, кабинеты, расписания, клиенты, записи, история, диалоги VK, входящие события, результаты действий и очереди сообщений находятся в общих физических таблицах с `salon_id`. Индексы и внешние ключи учитывают владельца. PostgreSQL RLS включён с FORCE; без контекста салона закрывает доменные строки для обычной роли. Приложению нужен пользователь БД **NOSUPERUSER NOBYPASSRLS**, владеющий схемой для миграций. Superuser/BYPASSRLS не обеспечивают эту защиту. Прямой доступ клиентов к БД не предоставляется.

Мастер имеет общую техническую личность `shared_masters` и отдельный профиль `masters` в каждом салоне. Услуги и часы профиля независимы. Его занятость проверяется между салонами; exclusion constraint запрещает пересекающиеся подтверждённые записи одного человека. Кабинет и клиент/телефон проверяются внутри салона. Подтверждённые записи поддерживают isolation level READ COMMITTED; DB guard отклоняет другие уровни. Общий advisory lock пока сохраняет последовательное выполнение команд; производительность нескольких салонов не измерялась.

## Конструктор данных

Каноническая модель: `entity_types`, `entities`, `entity_parameters`, `entity_parameter_values`. Значения хранятся в отдельных типизированных колонках: string, integer, number, boolean, date, reference. Ограничения проверяют тип, обязательность и принадлежность ссылки тому же салону и объявленному типу.

Доменные таблицы — совместимые проекции. Их изменения через существующие сервисные команды и канонические значения синхронизируются триггерами в одной транзакции. Системные типы/поля generic API менять не позволяет: услуги, мастера, кабинеты и часы редактируются через прежние команды, включая подтверждение отмены затронутых записей. Дополнительные поля системных типов допускаются только необязательными. Для собственных справочников доступны создание типов, полей и записей; обязательные поля допустимы. Заполненное поле нельзя удалить или сменить его тип без предварительной очистки данных.

Если салонов ещё нет, после входа открывается создание салона. Сервер атомарно создаёт салон и членство вошедшего администратора. Затем администратор собирает его: услуги → мастера → кабинеты → часы и перерывы. Новый ресурс не получает часы автоматически. Во вкладке «Свои справочники» создаются дополнительные типы данных. Общего мастера можно подключить из другого салона, доступного тому же аккаунту; глобальный ID сам по себе права на подключение не даёт.

## API

Вход, сессия и выход остаются `/api/login`, `/api/session`, `/api/logout`. В session/login добавлен `salons: [{id,name,role}]`; `/api/salons` возвращает доступные салоны. Все запросы выбранного салона требуют **X-Salon-Id**. Создание салона не требует выбранного салона. Сервер проверяет членство для каждого запроса; отсутствие выбора — 422, чужой салон — 403. Все POST кроме входа также требуют сессию и `X-CSRF-Token`.

- `POST /api/salons`: `{name,action_key}` — создание и автоматическая привязка к вошедшему администратору; ответ `{id,name,role,salons}`. Без X-Salon-Id, с сессией и CSRF. Повтор того же ключа возвращает тот же салон. Переданный браузером user_id не назначает права.
- `GET /api/salon`, `POST /api/salon {name}` — сведения и переименование выбранного салона. Название сохраняется канонически в конструкторе; ID и права не меняются. Услуги, мастера, кабинеты и часы редактируются прежними сервисными командами.
- `GET /api/vk` — публичное состояние привязки выбранного салона без секретов.
- `POST /api/vk/connect`: `{community,token,callback_origin}` — проверка ключа и постановка настройки; 202, затем опрос GET. callback_origin — HTTPS origin сайта, совпадающий с Origin запроса.
- `POST /api/vk/retry`, `/api/vk/check`, `/api/vk/disconnect`: `{}` — продолжить настройку, проверить без тестового сообщения, отключить.

- `GET /api/snapshot?date=YYYY-MM-DD`: каталог, расписание, записи выбранного салона; строки каталога содержат `entity_id`.
- `POST /api/services`, `/api/services/{id}`: создание/редактирование услуги `{name,duration_minutes,active?}`.
- `POST /api/masters`, `/api/rooms` и варианты `/{id}`: `{name,service_ids,active}`.
- `POST /api/weekly-schedule`: `{resource_kind,resource_id,weekday,intervals:[{start_minute,end_minute}]}`; пустые интервалы означают выходной.
- `POST /api/weekly-schedule/batch`: `{resource_kind:"master"|"room",resource_id,days:[{weekday:0..6,intervals:[{start_minute,end_minute}]}]}` — атомарно заменяет от 1 до 7 выбранных дней одного ресурса. Дубликаты дней, неверные минуты и пересечения — 422; ресурс вне выбранного салона — 404. Пустые интервалы означают выходной. Если график затрагивает действующие подтверждённые записи, возвращает 409 с `affected_booking_ids` без изменения расписания; этот endpoint никогда не отменяет записи, даже с `acknowledge:true`.
- `POST /api/availability-preview`: `{service_id,master_id,date:"YYYY-MM-DD",draft?:{resource_kind,resource_id,days:[...]},drafts?:[...]}` — возвращает `{slots:[ISO UTC],timezone,date,draft_applied,constraints:[string],empty_message:string|null}`. Можно передать один `draft` или массив `drafts` для не более 100 ресурсов; оба поля одновременно и повтор одного ресурса/дня запрещены. Проверяет фактические активные услуги и связи, графики, длительность, занятость/блокировки, горизонт и минимальное время до записи через тот же движок, что используется при записи. Черновики заменяют только недельные интервалы выбранных дней ресурсов в памяти; датированные исключения и закрытые интервалы сохраняют приоритет. Записи и черновики не сохраняются. Требует сессию, CSRF и выбранный салон, как остальные POST. Свободное окно не резервируется; занятость конкретного клиента без его данных не проверяется.

Проверка новых API (2026-10-06): 15 тестов `tests/test_constructor_ux.py` прошли на одноразовой PGlite 18.3 под ролью `NOSUPERUSER NOBYPASSRLS`; 8 независимых сценариев бэкенда и 16 сценариев интерфейса с настоящим HTTP также прошли. Проверены конфликты без отмены записей, атомарный откат при ошибке второго дня, текущий приём, связи/активность ресурсов, исключения по дате, блокировки/занятость, два черновика, правила записи, часовой пояс и изоляция салонов. Полный локальный suite без native URL: 77 тестов, 29 прошли и 48 пропущены. Для native PostgreSQL запустите `docker compose -f compose.test.yml run --build --rm tests`: добавлены отдельная БД и `CONSTRUCTOR_UX_TEST_DATABASE_URL`. Этот контейнерный прогон, реальная конкурентность PostgreSQL, браузерная визуальная проверка и production rollout в этой ревизии не выполнены. Существующие схемы и миграции не меняются. Выпускайте бэкенд перед новой версией конструктора LeraFront.
- `GET /api/shared-masters`: профили из других доступных салонов.
- `POST /api/masters/attach`: `{source_salon_id,master_id,service_ids,active?,name?}`.
- `GET /api/constructor`: системные и собственные типы, параметры и записи текущего салона.
- `POST /api/constructor/types`: `{code,label}`; `/{id}` меняет label собственного типа.
- `POST /api/constructor/parameters`: `{entity_type_id,code,label,data_type,required?,reference_type_id?}`; `/{id}` меняет описание/тип/обязательность собственного незаполненного поля. При переходе со ссылки к scalar нужно `reference_type_id:null`.
- `POST /api/constructor/entities`: `{entity_type_id,values:{code:value}}`; `/{id}` принимает `{values}`. Для системной записи — только дополнительные поля.

Изменение доступности через прежние команды, затрагивающее записи, сначала возвращает 409 и ничего не меняет. Повтор с `acknowledge:true` сохраняет прежние правила отмены/оповещения. Новая пакетная команда расписания всегда сохраняет записи и отклоняет затрагивающий их график. Встреча, уже начавшаяся, этим изменением не отменяется. Идемпотентность, VK ID и ключи сообщений разделены по салонам.

## Миграция и управляемое добавление салонов

`python app.py` применяет миграции до версии 5 атомарно до запуска HTTP. Старые строки переходят в салон 1 с прежними ID; история, аккаунты и сессии сохраняются. На существующей версии 4 старт добавляет технические таблицы версии 5 и атомарно обновляет функции, триггеры и политики без повторного переноса данных, изменения пароля или правил салона. Версия выше 5 выбранной схемы отклоняется до DDL. Технические `vk_connections` и `salon_creation_requests` хранят маршрутизацию/зашифрованные секреты и идемпотентность, отдельно от канонических доменных данных конструктора. Повторные UPSERT канонической проекции сохраняют её entity_id; пустой кандидат отклонённой вставки с новым ID удаляется после SQL-оператора. `SALON_POLICY_JSON`, если задан при первой миграции, переносится в настройки первого салона. После миграции правила берутся из типизированных настроек салона; изменение переменной не перезаписывает их.

Для первого запуска нужны только `DATABASE_URL` и `SALON_ADMIN_PASSWORD`. Логин по умолчанию `salon_admin`; `SALON_ADMIN_USERNAME` остаётся необязательным переопределением. Первый аккаунт создаётся только при отсутствии аккаунтов. Пароль 12–256 символов; пример отклоняется. Удалите bootstrap password из настроек после входа; последующим запускам достаточно `DATABASE_URL`. Отключённые аккаунты восстанавливает разработчик. Допускаются несколько активных аккаунтов; новые аккаунты не получают доступ ко всем салонам автоматически.

Команды выполняются разработчиком с DATABASE_URL в окружении, без секретов в аргументах:

```sh
python initialize.py
python provision_admin.py new_admin --salon-id 1
python manage_salons.py create "Название второго салона" --user-id 1
python manage_salons.py grant 2 1
python manage_salons.py revoke 2 1
python ops.py verify
```

Новый салон получает собственные описания системных типов и стандартные правила записи, пустой каталог и часы. `provision_admin.py` создаёт аккаунт или явно меняет его пароль, отзывая сессии. Первый аккаунт имеет доступ к салону 1; доступ остальных назначается явно.

Предыдущий backend, поддерживающий максимум версию 4, отвергает схему 5. Для возврата версии нужен согласованный план восстановления базы; простой запуск старого schema_postgres.sql поверх новой БД запрещён. `seed_starter.py` остаётся только синтетической фикстурой для свежей пустой БД.

## Переменные и VK

Сценарий записи VK: услуга → мастер → свободный день → свободное время → телефон → подтверждение. Дни определяются по наличию хотя бы одного окна для выбранной услуги и мастера в часовом поясе и горизонте записи салона. Используется тот же расчёт, что проверяет длительность, графики мастера/кабинетов, исключения, блокировки, занятость и интервалы между записями. Поиск дней останавливается на первом доступном окне каждого дня.

Даты и время показываются страницами по восемь вариантов, по две кнопки в ряд; «Раньше»/«Позже» листают список, «Другой день» возвращает к датам. Если дней нет, доступны повторная проверка и меню. Выбранный день и время пересчитываются при нажатии; неподходящее или устаревшее значение не продолжает запись. Каждый обновлённый список получает новую версию выбора: старая кнопка подтверждения не может подтвердить другую дату/время. Версия остаётся стабильной от выбора окна до атомарного подтверждения и его повтора. Конфликт при атомарном подтверждении возвращает актуальные окна или календарь дней. Ручной ввод даты ДД.ММ.ГГГГ остаётся совместимым. Перенос использует тот же календарь, исключая прежнюю запись из расчёта доступности; окончательные проверки переноса сохраняются.

Контракт календарного диалога проверяется `python -m unittest discover -s tests -p test_vk_calendar.py`: основной путь, все страницы дней/окон, пустой период, исчезнувшие окна, старые/неверные кнопки, конфликты подтверждения, перенос, часовой пояс и DST. Контрактные двойники не подтверждают реальные данные PostgreSQL и VK-доставку.

В Timeweb вводятся только `DATABASE_URL` и начальный `SALON_ADMIN_PASSWORD`; на фронте — `BACKEND_URL`. Порт 8080, Docker-схема lera, логин salon_admin и начальная политика уже заданы приложением. Политика берётся из того же `starter_data.json`, что использует первая миграция; каталог автоматически не загружается. Явные `PORT`, `DATABASE_SCHEMA`, `SALON_ADMIN_USERNAME`, `SALON_POLICY_JSON` остаются доступными переопределениями.

CSRF-токен по умолчанию выводится HMAC-SHA256 из случайного 256-битного токена сессии с отдельной меткой назначения; cookie не выдаётся в JSON. Он стабилен после перезапуска, привязан к сессии и проверяется после аутентификации. Отдельный глобальный секрет и новая таблица не нужны. Старый `SALON_CSRF_SECRET`, если явно задан, сохраняет прежний HMAC-режим; короткое/шаблонное значение отклоняется. При переходе с явного секрета на режим по умолчанию обновить страницу, чтобы получить новый CSRF-токен через `/api/session`; аккаунт и сессия сохраняются. Ключи БД/пароли остаются только на бэке. `/livez` проверяет процесс, `/healthz` — подключение и версию схемы.

Самостоятельное подключение находится во вкладке «ВК-бот». Для всей установки один раз задаётся `VK_TOKEN_ENCRYPTION_KEY` (Fernet); без него календарь работает, мастер сообщает, что подключение ещё не включено. Генерация:

```sh
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Сохраните этот приватный ключ с резервной копией и между деплоями. Простая замена переменной не является ротацией: старые данные перестанут расшифровываться. Потеря ключа требует отключения/повторного подключения и, если удаление не удалось, ручной уборки старого Callback-сервера.

Администратор указывает ссылку/ID сообщества и один раз вставляет ключ сообщества с правами `messages` и `manage`. Backend проверяет ключ, шифрует token/secret/confirmation, создаёт и подтверждает свой Callback-сервер, включает события message_new и применяет привязку без перезапуска. Callback доступен через `https://ФРОНТ/api/vk/callback/<connection_id>`; Nginx уже проксирует этот путь. Один салон — одно сообщество; одно сообщество — одна привязка. Поздняя авторизация ВК сможет передать ключ тому же механизму; OAuth сейчас не реализован.

Для новых Callback-серверов секрет создаётся как 48 ASCII hex-символов (192 бита случайности): это консервативный алфавит из латинских букв и цифр внутри лимита ВК в 50 символов. Ранее сохранённый секрет вне `[A-Za-z0-9]{1,50}` заменяется только перед новым созданием, после поиска сервера с прежним секретом и проверок конфликта, дубликатов, режима проверки и неопределённого результата. Зашифрованный новый секрет сохраняется вместе с `creation_ambiguous=true` до обращения к ВК, чтобы подтверждение и последующий readback использовали одно значение. Секрет существующего или неопределённо созданного сервера сохраняется. Это мера совместимости; код ВК 100 сам по себе не доказывает отказ из-за алфавита секрета.

При отказе ВК в журнале backend появляется `VK_API_REJECTED method=… vk_error_code=…`. Это имя вызванного метода и числовой код ВК; текст ответа, значения параметров запроса, токен и Callback-секрет не выводятся. Для ошибки 100 метода `groups.addCallbackServer` добавляется `vk_error_param=group_id|url|title|secret_key|unknown`: только одно распознанное имя параметра из фиксированного списка, включая написания `group id`, `secret key` и `server address`. Перед распознаванием из текста убираются значения переданного токена и параметров. Неоднозначное, отсутствующее указание поля, неизвестный формат текста или некорректный/отсутствующий код обозначается `unknown`. Сообщение `vk_rejected` само по себе не доказывает нехватку прав: для известных ошибок доступа используется `vk_permissions`. Точный отказ нужно проверить по журналу перед изменением ключа или настроек сообщества.

При неизвестном результате создания сервер сначала ищется в ВК по собственным URL/title/secret. Если результат не найден, повторное создание автоматически запрещено, чтобы не получить дубликат. Чужие серверы не меняются. Отключение сразу очищает секреты и подавляет старую очередь/диалоги выбранного салона; неудачное удаление в ВК показывается как предупреждение. Начавшийся внешний send отменить невозможно; новый send сериализуется с отключением. Отказ конкретному клиенту и временная недоступность ВК сохраняют failed-сообщение для повторов, не отключая остальных клиентов. Ошибка ключа при отправке переводит привязку в needs_attention.

Старые переменные поддерживаются для существующей установки. После первого подключения через мастер legacy Callback и sender для этого салона подавляются, включая состояние disconnected.

Legacy VK не включается без конфигурации. Один набор прежних VK_GROUP_ID/CALLBACK_SECRET/CONFIRMATION_CODE/COMMUNITY_TOKEN привязывается к VK_SALON_ID (по умолчанию 1, прежний салон). Несколько сообществ задаются приватной VK_INTEGRATIONS_JSON — массивом `{salon_id,group_id,secret,confirmation_code,token?,api_version?,master_photo_ids?}`. Каждый салон поддерживает одно сообщество VK; одно сообщество имеет одну привязку. Несколько сообществ одного салона отклоняются, чтобы его очередь не отправлялась чужим токеном. Не смешивайте JSON и прежние переменные. callback выбирает привязку по group_id и проверяет secret; worker использует отдельную очередь и токен привязки. Токены в конструктор и на фронт не попадают. Реальную отправку этой версии не проверяли.

Одноразовая отправка требует явной привязки:

```sh
python send_outbox.py --salon-id 1 --group-id 123 --limit 50
```

## Проверки

```sh
python -m compileall -q .
python -m unittest discover -s tests -v
```

Без переменных *_TEST_DATABASE_URL интеграционные проверки пропускаются; это не PASS базы. Для обычного PostgreSQL 16 подготовлены семь отдельных одноразовых БД и роль без обхода RLS:

```sh
docker compose -f compose.test.yml up --build --abort-on-container-exit --exit-code-from tests
docker compose -f compose.test.yml down
```

Набор проверяет прежние запись/конструктор/старт, перенос данных версии 3, typed EAV, внешние ссылки, RLS, ограничения и API нескольких салонов, общих мастеров и VK namespaces. Дополнительная namespace_test проверяет отдельную lera рядом с чужими public-таблицами и функциями, повтор миграции и UPSERT без лишних canonical entities. Compose использует временный локальный PostgreSQL и синтетические пароли; никаких production credentials. Эта команда в текущей среде не выполнялась: Docker и обычный PostgreSQL недоступны.

Статус проверки текущей версии — в `VERIFICATION.md`. Исторические результаты прежнего односалонного приложения на PG16/Chrome не подтверждают эту миграцию. Проверка обычного PostgreSQL, браузерного рендера, Docker-сборки, Timeweb, TLS/backup restore и реальной VK-доставки ещё нужна перед выпуском. Настройка Timeweb — в `TIMEWEB.md`.
