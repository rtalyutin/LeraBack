# Запуск Lera в Timeweb Cloud с БД tg-mcp

Создаются **два приложения**: LeraBack и LeraFront. Используется существующая PostgreSQL **та же база, что у tg-mcp**, и отдельная SQL-схема `lera`. Все салоны Lera хранятся в общих таблицах этой схемы с `salon_id`. Каталог, мастеров, кабинеты и часы администратор собирает через интерфейс.

## 1. Подготовка существующей БД

До первого старта подтвердить кластер и **имя базы** tg-mcp, сохранить резервную копию и подготовить схему. Название приложения tg-mcp не обязательно совпадает с именем базы; HOST/PORT/DBNAME берутся из его реального подключения. URI и пароли в чат или GitHub не отправляются.

В [rtalyutin/Tg-mcp](https://github.com/rtalyutin/Tg-mcp/blob/main/DATABASE-MCP.md) существующее подключение задаётся `DATABASE_URL`. Возьми HOST/PORT/DBNAME из действующего значения в настройках приложения tg-mcp; в URI Lera используй логин/пароль `lera_app`. Команды его database MCP работают с существующими строками и не выполняют DDL — создать роль и схему через read_database/write_database нельзя.

Для Lera создать отдельного пользователя `lera_app`: NOSUPERUSER, NOBYPASSRLS, владелец схемы `lera`. Не выдавать ему полные права на все базы и таблицы tg-mcp. В Timeweb пользователь создаётся на вкладке «Пользователи» с настройкой привилегий; на минимальном тарифе создание дополнительных пользователей через панель недоступно. Если это ограничение встретится, сначала проверить доступное управление ролями; не менять тариф автоматически.

Администратор БД выполняет следующие команды **в уже выбранной базе tg-mcp**, после создания пользователя. Это подготовка, команды на рабочей БД пока не выполнялись:

```sql
-- Проверить, что подключение выбрано правильно и роль существует.
SELECT current_database(), version();
SELECT rolname, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = 'lera_app';

-- Создать новую схему; при существующей lera остановиться и проверить владельца/содержимое.
CREATE SCHEMA lera AUTHORIZATION lera_app;
REVOKE ALL ON SCHEMA lera FROM PUBLIC;

-- Приложению нужны подключения и временные представления для области салона.
DO $$ BEGIN
  EXECUTE format('GRANT CONNECT, TEMPORARY ON DATABASE %I TO lera_app', current_database());
END $$;
```

Миграции создают таблицы, функции и индексы внутри заранее подготовленной схемы. `public` не добавляется в поиск объектов Lera. Расширение `btree_gist` не требуется; существующие расширения tg-mcp не перемещаются. Изменение `DATABASE_SCHEMA` выбирает другую область хранения и **не переносит** прежние данные Lera из `public`; для существующей установки перенос оформляется отдельно.

Подключение бэка:

```text
postgresql://lera_app:PASSWORD@TG_DB_HOST:TG_DB_PORT/TG_DB_NAME?sslmode=require
```

Спецсимволы логина/пароля кодируются для URI. Адрес должен быть доступен приложению, с поддерживаемым TLS. Если БД подключается только через приватную сеть, назначить бэку эту сеть при создании; Timeweb не позволяет сменить приватную сеть после деплоя. Реальную связность и TLS нужно проверить на целевом сервисе.

Источники: [пользователи PostgreSQL](https://timeweb.cloud/docs/dbaas/postgresql/users-and-privileges), [подключение](https://timeweb.cloud/docs/dbaas/postgresql/connect-to-database).

## 2. Настройки приложений

Оба сервиса разворачиваются через **Dockerfile**, включая Nginx фронта. Команды сборки и запуска берутся из файлов репозитория; отдельные npm-команды не нужны.

| Поле панели | LeraBack | LeraFront |
| --- | --- | --- |
| Название | `lera-back` | `lera-front` |
| Репозиторий | `rtalyutin/LeraBack` | `rtalyutin/LeraFront` |
| Ветка | `main` | `main` |
| Фреймворк / сборка | `Dockerfile` | `Dockerfile` |
| Путь к директории проекта | Пусто | Пусто |
| Dockerfile | В корне | В корне |
| Порт контейнера | `8080`, уже указан через EXPOSE | `8080`, уже указан через EXPOSE |
| Путь проверки состояния | `/livez` | `/healthz` |
| Запуск | `python app.py`, уже задан в Dockerfile | Стандартный запуск Nginx из образа |
| Приватная сеть | Та, из которой доступна БД, если требуется | Доступ к HTTPS-адресу бэка |
| Автодеплой при первом запуске | Выключить «Сборка по последнему выполненному коммиту» | Выключить ту же опцию |

Внешний доступ идёт через HTTPS-адрес сервиса; открывать 8080 в адресе сайта не требуется. Ресурсы выбираются в панели по доступной конфигурации; нагрузка текущей версии ещё не измерена. Постоянный диск приложений не требуется для записей: они хранятся в PostgreSQL.

Источники: [Dockerfile](https://timeweb.cloud/docs/apps/deploying-with-dockerfile), [healthcheck](https://timeweb.cloud/docs/apps/healthcheck-path).

## 3. Переменные LeraBack

Создать **локальные** переменные бэка, не отмечать «Сохранить как глобальную». В панели вводится значение без внешних кавычек.

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | URI из раздела 1: существующая база tg-mcp, пользователь `lera_app` |
| `SALON_ADMIN_PASSWORD` | Свой пароль 12–256 символов, только для первого старта |

```dotenv
DATABASE_URL=postgresql://lera_app:PASSWORD@TG_DB_HOST:TG_DB_PORT/TG_DB_NAME?sslmode=require
SALON_ADMIN_PASSWORD=СВОЙ_ПАРОЛЬ_12_256_СИМВОЛОВ
```

Это весь обязательный набор первого запуска. После создания аккаунта остаётся только `DATABASE_URL`. VK-переменные пока оставить незаданными.

Приложение уже задаёт порт `8080`, Docker-схему `lera`, логин `salon_admin` и согласованную политику: Москва, месяц вперёд, шаг 30 минут, запись минимум за 2 часа, без подготовки между записями, отмена/перенос за час. Политика первой миграции берётся из `starter_data.json`; дальнейшие настройки салонов хранятся в БД. Услуги и расписание создаются через конструктор.

CSRF-защита работает автоматически от случайной сессии и сохраняется после перезапуска; отдельный `SALON_CSRF_SECRET` вводить не нужно. Переопределения `DATABASE_SCHEMA`, `PORT`, `SALON_ADMIN_USERNAME`, `SALON_POLICY_JSON`, `SALON_CSRF_SECRET` поддерживаются для существующих установок, но для этого запуска не требуются. Для старой установки в public явно оставить `DATABASE_SCHEMA=public`: новое имя схемы не переносит данные. Локальные команды вне Docker без переменной используют public.

При старте `python app.py` применяет миграцию 4 и создаёт первого администратора в `lera`, если аккаунтов ещё нет. Для уже созданной версии 4 обновляются её функции и триггеры; аккаунты, сессии и настройки сохраняются. Версия схемы выше 4 отклоняется до изменения её объектов. Тестовые услуги и мастера не добавляются. Отдельные команды `initialize.py` и `provision_admin.py` при обычном первом старте не нужны. Необязательный SALON_POLICY_JSON импортируется только при первой миграции; затем изменение переменной не перезаписывает настройки.

После запуска проверить:

1. В логе есть `Database initialized; administrator ready`, без ошибки миграции.
2. `https://АДРЕС-БЭКА/livez` возвращает 200 — процесс работает.
3. `https://АДРЕС-БЭКА/healthz` возвращает 200 и `{"status":"ok"}` — схема БД готова. 503 означает, что подключение или версия схемы требуют проверки; поддерживается ровно версия 4.
4. Команда `python ops.py verify` в окружении бэка подтверждает выбранную схему.

Источники: [переменные App Platform](https://timeweb.cloud/docs/apps/variables). Реальные параметры подключения пока не получены.

## 4. Переменная LeraFront и порядок запуска

Единственная переменная фронта:

```text
BACKEND_URL=https://АДРЕС-БЭКА
```

Указать HTTPS origin без завершающего `/`, без `/api` и других путей. Внешние кавычки не вводить. Данные доступа к PostgreSQL и начальный пароль остаются в бэке. Nginx проксирует `/api/` и сохраняет один origin для браузерной сессии; CORS отдельно настраивать не нужно.

Порядок: подготовить роль и схему → запустить бэк и проверить `/healthz` → вставить его адрес в BACKEND_URL → запустить фронт → войти с начальным логином и паролем → выбрать салон и собрать каталог/расписание.

После успешного входа удалить SALON_ADMIN_PASSWORD из переменных бэка и применить настройки. Существующий аккаунт останется; повторный запуск не меняет его пароль. Если это обновление старого запуска с явным SALON_CSRF_SECRET, его можно оставить для сохранения прежних CSRF-токенов; после удаления обновить страницу, чтобы получить токен новой схемы. Пароль/сессии от этого не меняются.

## 5. Проверка и обновления

Создать услугу, мастера, кабинет, часы с перерывом и тестовую запись. Проверить отказ при пересечении и сохранность после перезапуска. Добавление салонов/аккаунтов и прав выполняется разработчиком через команды README. Не пересоздавать рабочую БД при ошибке подключения.

Перед рабочим запуском нужен полный прогон текущей версии на обычном PostgreSQL; Docker, Timeweb, TLS и backup/restore здесь не подтверждены. Локальные проверки и ограничения — в VERIFICATION.md. Применение SQL в базе tg-mcp, создание роли/схемы и деплой приложений ещё не выполнены. Состояние автодеплоя в панели не проверено.

Для обновления сохранять совместимую пару LeraBack/LeraFront. Старый backend несовместим со схемой 4. Откат кода не восстанавливает данные: возвращение старой модели требует отдельного плана восстановления. Резервная копия общей базы включает и tg-mcp, поэтому восстановление всей базы нужно согласовывать с обоими сервисами.
